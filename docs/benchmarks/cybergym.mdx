# CyberGym

QitOS integrates CyberGym as a benchmark family with a dedicated agent runtime under `qitos/benchmark/cybergym/`.

<Tip>
Running long batches on a dedicated host? See [Deploy CyberGym batches on a server](/guides/cybergym-server-deployment) for systemd units, Docker image preparation, grading keys, and sizing.
</Tip>

## Current Integration Notes

The current integration is optimized for long-running PoC-generation tasks and keeps the benchmark-specific logic split across:

- `qitos/benchmark/cybergym/runtime.py`
- `qitos/benchmark/cybergym/runner.py`
- `qitos/recipes/benchmarks/cybergym.py`
- `qitos/benchmark/cybergym/agent/`

## Important Runtime Behavior

### 1. Task workspace layout

Single-task recipe runs now place prepared task files under:

```text
<out_dir>/workspace/<task_slug>/
```

instead of writing task files directly into `<out_dir>`.

This keeps:

- benchmark-level files such as `run.log`, `traces`, and `server_poc` at the experiment root
- task-local files such as `repo-vul`, `submit.sh`, `.cybergym`, and generated PoCs inside the task workspace

### 2. Model transport defaults

OpenAI-compatible harness presets now default to:

- request timeout: `120s`
- lightweight retry on transient request failures, including timeout cases

This is handled in the shared OpenAI-compatible model layer rather than only in the benchmark wrapper.

### 3. Run-level inference sticky routing

CyberGym agent runs generate a run-unique inference `task_id` such as:

```text
cybergym-arvo-3938-<run-uuid>
```

QitOS sends this value on every OpenAI-compatible model request as:

```text
x-inspire-inference-key: <inference task_id>
```

This keeps all LLM requests for one agent run routed to the same upstream backend node while allowing repeated runs of the same CyberGym benchmark task to spread across nodes. The CyberGym benchmark `task_id` used for `submit_poc` and checksum validation is not changed. The generated inference `task_id` is printed near the start of the TUI and `tui.log` agent-composition block.

For non-CyberGym callers, `QITOS_INFERENCE_KEY` remains a compatibility fallback when no model-level `inference_key` is provided.

### 4. Tool-result budget

CyberGym benchmark runs use a larger tool-result budget than the generic engine default.

The current CyberGym runner sets:

```text
tool_result_max_chars = 60000
```

This reduces destructive truncation for long `READ` and `BASH` outputs during exploit-development tasks.

### 5. Mask-map enabled verification servers

When the CyberGym verification server runs with `--mask_map_path`, it only
accepts submissions that carry the **masked** task id. The prepared task
package must therefore be generated with the same mask map, otherwise every
`submit_poc` fails with `Invalid task_id`.

Set the mask map path for the run:

```text
CYBERGYM_MASK_MAP=/path/to/mask_map.json
```

`CYBERGYM_MASK_MAP_PATH` is accepted as an alias. The task package then embeds
the masked id and the matching checksum in `submit.sh`, and the server can
unmask it for grading.

## Agent-Side Context Retention

The CyberGym agent keeps the full step chain and uses content-level compression rather than round deletion:

- full step history is retained
- the newest 10 distinct steps remain raw
- the earliest 3 distinct steps remain raw
- older long tool results are moved into artifacts with preview metadata

## Verification Focus

For public-server runs that only expose vulnerable-binary behavior:

- `verification_scope == "vul_only"`
- `vul_exit_code != 0`

is treated as a success stop condition by the CyberGym agent/runtime contract.

## Local Validation

The integration is covered by targeted tests around:

- recipe workspace layout
- history retention and compaction
- model retry and timeout defaults
- runtime prompt/tool-path preservation

End-to-end local runs against a real CyberGym verification server are recorded
in `docs/internal/cybergym-local-test-report.md`, including the per-task
outcomes and the runtime prerequisites (mask map, staged binary, agent image).

Latest local run: 10 tasks attempted, 8 passed, 1 failed in preflight, 1 still
running. The passing set spans both families (`arvo` and `oss-fuzz`), with PoCs
between 4 bytes and 2.7 KB.

### Operational prerequisites

These bite silently, so check them before blaming the agent:

- **Mask map**: when the server runs with `--mask_map_path`, set
  `CYBERGYM_MASK_MAP` to the same file. Otherwise every `submit_poc` is
  rejected with `Invalid task_id`.
- **One executable in the staged directory**: the agent's binary discovery
  fails closed (`ambiguous_executable_candidates`) when `/out` holds more than
  one executable, so keep only the target fuzzer executable and leave data
  files non-executable.
- **`vm.mmap_rnd_bits`**: the prebuilt fuzzers need `28` in the container
  runtime kernel; a newer default breaks them at startup.
- **Import cost**: importing the agent from a Windows-mounted path (9p/DrvFs)
  takes minutes. Keep the runtime copy, task data, staged binaries, workspaces,
  and traces on a local Linux filesystem.
